# Roadmap Spec — Multi-Region Secret Replication (v1.7)

**Date:** 2026-08-06
**Issue:** [#12](https://github.com/hackeshackes/deerfllow-BY/issues/12)
**Status:** backlog — grooming only, no implementation this iteration

## Problem

The owner-only admin-secrets vault (M1) writes to a single Fernet vault file on one region's disk; `rotate` re-encrypts in place. A multi-DC deployment cannot tolerate this — if the writing region goes down, other regions cannot decrypt `/api/admin/secrets`. Issue #12 defers cross-DC replication to v1.7.

## Goals

- Replicate the vault file across regions via **object storage** (S3 / GCS / Aliyun OSS).
- Gateway startup pulls from the **nearest** region (or fetches from primary if the local copy is missing), caching `vault_mtime` in memory.
- **Encryption at rest** in object storage via envelope encryption (KMS data keys; KMS keys per region).
- Audit events `admin_secret.replica_pulled` / `admin_secret.replica_pushed`.

## Non-goals

- Multi-writer within a region (stays single-writer per region).
- Changing the single-owner rotate semantics.
- Realtime/strongly-consistent replication — **read-mostly, sparse writes** is the accepted model.

## Proposed shape

### Storage adapter

- `backend/packages/harness/deerflow/admin/replication.py` — a `SecretReplicator` Protocol with S3/GCS/Aliyun OSS adapters. Prefer existing `httpx` for REST-capable providers (Aliyun OSS); `boto3`-equivalent only where REST is insufficient.
- Conflict resolution: latest `mtime` wins + a write-lock; refuse and surface a clear error on concurrent writers (split-brain).
- Envelope encryption: root KMS key per region wrapping a per-vault data key; the vault file on object storage is never cleartext.

### Gateway wiring

- Startup: attempt nearest-region replica; on miss → fetch from primary; keep `vault_mtime` in memory for invalidation (mirrors the existing secrets read-path that swallows decrypt failures to empty).
- `rotate` stays atomic per file; the cross-process flock from M2 remains.

## Acceptance criteria

- [ ] DR drill: kill primary region; gateway in secondary bootstraps and serves `/api/admin/secrets/status` from the replica within 60s.
- [ ] Split-brain: concurrent rotators — one refused, clear error surfaced.
- [ ] Encryption-at-rest via cloud KMS confirmed (no cleartext vault on object storage).
- [ ] No new hard external deps beyond boto3-equivalent or existing httpx.
- [ ] `admin_secret.replica_pulled` / `admin_secret.replica_pushed` events in `audit.jsonl`.

## Risks

- Single-writer model assumes one owner; multi-owner admins across regions need careful audit.
- Network partition during rotate may block for minutes — needs a timeout + admin-facing error.

## Affected files (reference)

- `backend/packages/harness/deerflow/admin/{secrets,replication}.py`
- `backend/app/gateway/routers/admin_secrets.py` — rate limit + audit wiring
- Config: new `secrets.replication` section in `config.yaml`

## Open questions

- Replication propagation trigger (periodic poll vs object-storage event) vs `vault_mtime` cache TTL.
- Recovery semantics when the primary is unreachable at rotate time.
