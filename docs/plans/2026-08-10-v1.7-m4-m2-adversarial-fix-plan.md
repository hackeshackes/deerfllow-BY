## B1 — SigV4 签名日期错误 [CRITICAL]

### 影响的文件
- `backend/packages/harness/deerflow/admin/s3_replicator.py`
- `backend/packages/harness/deerflow/admin/aws_kms.py`

### 预期 vs 实际
- **预期**：credential scope（`Credential=.../<DATE>/region/service/aws4_request`）与派生签名 key 的 `kDate` 都必须用 **`YYYYMMDD`**（AWS 规范）。
- **实际**：`s3_replicator.py` / `aws_kms.py` 用 `amz_date` 的**完整时间戳** `%Y%m%dT%H%M%SZ`。请求路径 `_request`/`_call` 固定设 `amz_date = now.strftime("%Y%m%dT%H%M%SZ")`，故 scope/key 携带 `.../20260810T120000Z/...` —— AWS 拒绝 → **生产环境每次真实请求必失败**。

### Why 旧测试没抓到
- 旧的 `test_signature_is_deterministic` 直接给 `sign()` 传**短日期** `"20260806"`（切 slice 无操作 → 恰好"正确"），从不走真实请求路径，因此 never exercise 完整时间戳。

### 复现（修复前）
真实路径（MockTransport 注入）对 `put()` 捕获 wire Authorization Signature，与按规范重算的期望比对：
- S3：`got=f772e872… want=642a3e42…`
- KMS：`got=91620cd8… want=c5715bb7…`

### 修复方案（已落地）
4 处统一对日期做 `amz_date[:8]`；`x-amz-date` HTTP header 与 string-to-sign 保留完整时间戳不变（**x-amz-date 本就必须全时间戳**）：
1. `s3._signature` → `plan_date = amz_date[:8]` 进 scope
2. `s3._authorization` → `scope = amz_date[:8]/...`
3. `kms._signature` → `plan_date` 进 scope + `_derive_signing_key(plan_date)`
4. `kms._authorization` → `scope = amz_date[:8]/...`

向后兼容：对已是短日期的输入 slice 是 no-op。

### 验证
- `test_s3_sigv4_attack.py::test_sigv4_matches_official_aws_test_vector` —— 复现 AWS 官方 GET 工作流，签名字节级等于官方 `f0e8bdb8…6db41`（**证明规范正确**）。
- `test_s3_sigv4_attack.py::test_wire_put_signature_recomputes_to_match` / `test_kms_wire_signature_recomputes_to_match` —— 端到端 wire 重算。
- 3 个 date-scope 反证测试：修复前 FAIL（旧代码）。
- 7 个参数化保留字符 canonical-URI 一致性 + body-hash 绑定 + 5xx 处理。

## B2 — push_local_to_replica 损坏 vault 读逃逸 [HIGH]

### 影响的
- `backend/packages/harness/deerflow/admin/replication_wiring.py`

### 根因
`push_local_to_replica` 在 `try/except` **之外**调用 `data = _read_secret_map()`（corrupt vault 解密成非 dict JSON → `RuntimeError("Admin secrets vault is corrupted.")`）。该函数文档/设计是 best-effort：传输错误(`mgr.push`)被吞+审计，但 **vault-read 错误却不吞** —— 不一致，未来直接调用者可能因此 500。

（生产未触发，因 `admin_secrets._replicate_after_write` 在外部兜底；但作为 best-effort 接口应自包含。）

### 修复（已落地）
把 `data = _read_secret_map()` + `json.dumps(...)` **移入** `try/except`。损坏读 → 吞 + 审计 `replica_pushed ok=false`，与其他复制失败一致。
```python
try:
    data = _read_secret_map()
    plaintext = json.dumps(...)
    await mgr.push(...)
except Exception as exc:
    logger.warning(...)
    record_replica_audit("pushed", ..., ok=False)
```
无调用方依赖旧的向上传递。

### 验证
- `test_replication_wiring_robustness.py::test_push_when_vault_read_raises_is_best_effort`
- `test_upsert_endpoint_returns_200_when_replication_push_fails`（端到端：真实 helper + patch 内层 push）

## B3 — list_workflows 授权泄露 [HIGH]

### 背景
- `backend/app/gateway/canvas/routers/workflows.py`

### 根因
`GET /api/workflows` 把 `workspace_id` 当作**普通 query 参数**直接 `store.list_by_workspace(workspace_id)`，`user` 仅在 `require_user` 解析后从未被校验。一个只属于 ws-a 的 member 通过 `/api/workflows?workspace_id=ws-b` 就能枚举 ws-b 的全部 workflow —— **逐 workspace 隔离的 list 边界敞开了**。

（单资源路由 `get/update/delete/…` 已经在 M2 B 中被 `_authorize_workflow` 加固为 404-hide，但 list 端点漏了。）

### 复现
`test_workflow_abac_matrix.py::test_list_workflows_leaks_unjoined_workspace` —— member(memberships=[ws-a]) 看到 ws-b workflow id。

### 修复（已落地）
新增 `_require_can_list_workspace(user, workspace_id)`：
- owner → 任意 ws 可列
- member → 仅当 `workspace_id ∈ list_workspaces_for_user(id)`；否则 `403 not a member of this workspace`

handler 开头调用。列表端点用 403（vs 单资源的 404 隐藏性）——因为 member 传他人 ws 属于明确越权尝试，403 不泄露资源存在性（漏洞类）。

### 验证
- `test_workflow_abac_matrix.py::test_list_workflows_member_cannot_list_unjoined_workspace`（修复前 FAIL，修复后 PASS）
- `test_list_workflows_member_sees_only_list_own_ws`（member 查询自己 ws → 200 且不跨界）
- owner 列任意 ws 由 owner→200 既有覆盖

## B4 — 测试隔离：auth `importlib.reload` 碎片化 [HIGH，测试稳定性]

### 背景
- `tests/test_workflow_abac_matrix.py`、`tests/test_workflow_abac_all_routes.py`

### 根因
两个文件用测试自身 import 的 `app.gateway.auth.require_user` 做 `app.dependency_overrides[require_user]`。前置的 `test_auth_secret_fail_fast.py` `importlib.reload(app.gateway.auth)` 会创建新的 `require_user` 函数对象；FastAPI 按对象 identity 匹配 override，于是 router 的 `require_user`（旧对象）与 override key（旧对象）应一致……实际因 reload 使 **router 模块里 `endpoint/handler` 引用与 override key 出现 identity 分裂**，override 失效 → 落到真实 `require_user` → `PYTEST_CURRENT_TEST` seed owner → 全部放行（假 200/200/…）。

单跑 matrix 文件 14 过；全量（或 `test_auth_secret_fail_fast` 之后）6 个假失败。（项目记忆 `deerflow-full-suite-known-failures` 已记录此 reload 坑，collab-publish 曾鉴 M1 修复。）

### 修复（已落地）
参照 M1 collab-publish 先例：**override key 用 `canvas.routers.workflows` 模块自身的 `require_user` 绑定**（`wfmod.require_user`），而不是测试 live 导入。
```python
import app.gateway.canvas.routers.workflows as wfmod
app.dependency_overrides[wfmod.require_user] = _as_user
```
这样即便 `auth` 被 reload，router 模块内捕获的 `require_user` 对象 = override key，identity 对齐。

### 验证
`CI=1 uv run pytest tests/test_auth_secret_fail_fast.py tests/test_workflow_abac_all_routes.py tests/test_workflow_abac_matrix.py -q` → 25 通过；全量 revert 到只留 2 个已知 `client_e2e`。
